# 从参考图像重建 UI

**使用时机**：任务是将截图或设计图像转换为页面、组件或应用程序 UI，使用 HTML/CSS 或项目现有的前端技术栈。将现有实现与其参考进行核对是相同的工作流程，从“验证”阶段进入。对于独立的图标、Logo 或插图，请阅读 `restore-graphic.md`；对于 Mermaid、Graphviz 或其他结构化图表，请阅读 `restore-structure.md`。

## 选择还原模式

- 当用户要求快速、粗略、近似、原型或首版重建，或明确优先考虑速度而非保真度时，使用**快速还原模式**。其目标是在项目已可运行的情况下，约三分钟内得到可识别的截图。
- 当用户要求高度接近、精确、像素级或生产就绪的对齐，或未选择更快的近似方案时，使用以下**标准还原工作流程**。

## 快速还原模式：约三分钟内获得首张截图

快速模式保留页面的层级结构、主要区域、可见文本和主要状态。它有意近似处理精细间距、精确颜色、字体排印、阴影、装饰细节和图标几何形状。

### 硬性限制

1. 在编写代码前检查现有前端技术栈、组件库、图标集、源资源和设计令牌，但一旦找到可用的本地原语就立即停止搜索。
2. 运行一次全图 `detect` 扫描。将其边界框视为布局估算，不要开始逐区域清点。
3. 在该次 `detect` 扫描之后，通过 `view_image`（或宿主环境等效的内置查看器）和 `glance` 进行最多**六轮顺序图像检查**。每轮最多可并发发起三个独立调用，因此六轮的硬性上限为 18 次调用。将不相关的区域或问题合并到同一轮中，而不是等待每个结果后再开始下一个调用。通常一两轮就足够了。
4. 在快速模式中不要使用 `trace`、前景提取、重复颜色采样或迭代式 `pixel_diff` 操作。这些是保真度工具，会消耗交付时间窗口。

### 构建近似实现

1. 首先实现最大的布局区域，然后是可见文本、主要控件和最重要的状态。忽略仅在放大时才可见的细节。
2. 复用项目现有的组件和 CSS 令牌。如果项目的前端或图标库包含合理相似的组件或图标，直接使用它，而不是重新创建参考。优先使用近似的库图标，而不是裁剪、描摹或手绘新图标。
3. 使用附近现有的调色板令牌或视觉上相似的 CSS 值。精确采样的十六进制值、渐变、细微边框和阴影不透明度不在范围内，除非其中某一项定义了整体构图。
4. 保持文本和控件为原生、可选择和可交互的。快速模式放宽的是视觉保真度，而非基本 UI 行为。

### 渲染一次、修正一次、交付

1. 使用 `scripts/html_shot.py` 或项目现有的浏览器设置渲染目标视口。仅当参考覆盖完整的滚动文档时才使用 `--full-page`；无论哪种方式，都保持相同的逻辑视口。
2. 检查截图一次。如果存在明显的结构性问题，如缺少主要区域、换行错误或比例严重失调，做一次有针对性的修正并再次渲染。
3. 交付截图。停止继续花费剩余时间处理微小的颜色、图标、字体、阴影、圆角或间距差异。

实际时间分配大致为：约 30 秒用于项目检查和 `detect`，90 秒用于实现，剩余一分钟用于启动、渲染、一次修正和截图交付。依赖安装或项目尚未可运行可能会延长该目标时间；不要通过悄悄切换回冗长的精确循环来弥补。

## 标准还原工作流程

### 核心策略：代码原生 UI 加截图支持的视觉元素

不要为整个页面选择单一的还原模式。分别对每个元素进行分类。大多数成品页面应结合两种类型：

| 类型 | 构建方式 | 典型示例 |
|---|---|---|
| **代码原生组件** | 复用项目的组件库，或使用语义化 HTML、CSS 和简单 SVG 原语构建 | 布局、文本、按钮、输入框、卡片、标签页、分隔线、背景、简单几何徽章 |
| **截图支持的视觉元素** | 提取原始像素，必要时移除背景，并将结果作为图像资源放置 | Logo、专有图标、插图、装饰性图案、纹理、复杂静态标记 |

对每个元素使用以下决策顺序：

1. **复用项目中现有的组件或源资源。** 在重新创建任何内容之前先搜索。
2. **使用代码原生组件**，当元素包含文本、接受输入、状态会变化、必须响应布局，或使用项目常规原语即可简单表达时。
3. **使用截图支持的视觉元素**，当元素是静态的、视觉上独特、重绘成本高且不存在源资源时。
4. 仅当用户要求 SVG/可编辑性、视觉元素必须缩放到超出截图分辨率，或提取无法干净地将其分离时，才重建矢量图形。该分支请遵循 `restore-graphic.md`。

切勿将文本、控件或大型布局块扁平化为截图。切勿仅仅为了让实现看起来更“原生”而重绘可提取的品牌图案。对于复杂小部件，保持外壳、文本和交互为原生；仅对其静态装饰层使用提取的图像。

## 步骤

### 1. 保存参考并检查目标项目

如果参考位于临时路径，在第一次工具调用前将其复制到持久工作存储。在编写替换代码之前，检查现有技术栈、组件库、字体、图标、图像和设计令牌。

### 2. 建立坐标系

记录参考图像尺寸和目标视口。截图可能是 HiDPI：`detect`、`ground` 和 `crop` 报告图像像素，而 CSS 使用逻辑像素。根据实际图像和视口尺寸推导缩放比例；不要假设固定的 2 倍比率。

### 3. 由外向内清点 UI

1. 运行一次全图 `detect` 扫描以获取初始元素列表和边界框。
2. 对密集布局块使用 `detect --region`；全屏扫描仅是脚手架。
3. 使用 `glance` 查看层级结构、组件类型、视觉状态和样式。
4. 使用 OCR 获取可见文本，对仍不明确的特定元素使用 `ground`。

将模型边界框视为近似句柄。用它们来组织页面，但不要将其最后几个像素误认为精确测量边界。

### 4. 实现前先分类

制作一个简短的元素列表，并为每个元素做出以下决策之一：复用现有源、代码原生、截图支持或混合。这可以防止两个代价高昂的错误：从头重建复杂图案，以及将功能性 UI 变成静态图像补丁。

### 5. 提取截图支持的视觉元素

使用带边距的裁剪仅用于检查和居中目标。在前景提取之前，将最终区域收紧到视觉元素自身的墨迹范围；区域内相邻的文本或线条也可能成为前景组件。

```bash
crop shot.png --region X1,Y1,X2,Y2 --scale 4 -o work/icon4x.png
python3 scripts/extract_fg.py work/icon4x.png

# 或直接从已知的紧凑区域提取：
python3 scripts/extract_fg.py shot.png \
  --region X1,Y1,X2,Y2 -o work/icon.png
python3 scripts/extract_fg.py shot.png \
  --region X1,Y1,X2,Y2 --mode dark -o work/logo.png
```

使用前检查透明结果。确认整个视觉元素完整存在，没有相邻文本或边框渗入，且 Alpha 边缘保持干净。提取多个资源时，在联系表中一起检查它们，而不是仅凭文件名确认。

### 6. 实现原生框架

- 遵循项目现有的框架和组件模式。
- 原生构建内容、交互、响应式布局、边框、阴影和简单形状。
- 使用 `scripts/dominant_colors.py` 获取重要的背景、文本和强调色值；使用 `glance` 来命名颜色，而不是凭空编造其数值。
- 以明确的逻辑尺寸放置提取的资源。保持其宽高比，避免将周围空白烘焙到资源中。
- 在调整微小间距之前，先匹配结构和比例。

## 按影响度验证和收敛

对于现有实现，从这里开始。

1. 使用 `scripts/html_shot.py` 或项目的浏览器测试设置，在相同的逻辑视口下渲染。对于长页面参考，添加 `--full-page` 而不是增加 `--height`，后者会改变基于 `vh` 的布局。
2. 在相同尺寸下比较渲染结果和参考。并排检查它们；使用 `scripts/pixel_diff.py` 定位难以发现或解释的差异。
3. 修复实质性差异：内容缺失或错误、层级结构不正确、换行错误、对齐或比例明显错误、组件状态错误、资源变形以及主色调明显不同。
4. 在有意义的修复后重新渲染。当比较仍暴露用户可见缺陷时继续；当剩余差异仅为字体光栅化、抗锯齿、亚像素定位或其他不可感知的渲染细节时停止。

`pixel_diff` 是定位工具，而非验收目标。不要仅仅为了降低其聚合百分比而持续迭代，也不要承诺在未单独限定浏览器、字体、视口和渲染环境的情况下，从截图实现零差异输出。

## 边界

- 不要将整个页面的截图作为实现交付。
- 不要使用截图支持的文本或控件，如果它们必须保持可选择、可访问、可交互、可本地化或可响应。
- 不要将提取的位图拉伸到超出参考所支持的分辨率。当需要缩放时，获取源资源或重建矢量图形。
- 始终与原始参考进行比较，切勿仅与你自己渲染的早期版本比较。
