# 上游出口显式化，仅故障时切换

状态：已接受

Vision 代理的上游请求使用了 `urllib` 的默认 opener，在 Windows 上会静默跟随系统代理；当用户的 Clash（127.0.0.1:7890）不可用时，每个上游请求都会被拒绝，导致整个 19100 链路返回 502。我们用显式的出口层替换了隐式 opener：请求默认直连（TCP+TLS），或通过可选的 `--upstream-proxy` CONNECT 隧道（`VISION_UPSTREAM_PROXY` 环境变量回退，`--proxy-first` 用于调整顺序），并且从不查询系统代理。

路由在内存中具有粘性：连接（TCP/TLS，5 秒套接字超时）成功的路由会被后续请求复用，仅当该路由建立连接失败时才进行切换——HTTP 层错误原样通过，没有定期重新探测，当所有路由都失败时，客户端会收到一个 502 响应，列出每条路由及其失败原因。较短的套接字超时保证了快速故障转移，而连接后的流式传输则保持了较长的 600 秒读取超时。没有指定端口的代理 URL 使用 HTTP 的标准端口 80，并且有意不支持代理认证。

考虑的方案：

- **继续跟随系统代理** — 已拒绝：这会使代理的行为依赖于机器级设置，该设置可能在代理运行期间发生变化，且本地代理失效会导致整个链路不可用。
- **完全绕过系统代理（`ProxyHandler({})`）** — 已拒绝：这会静默丢弃真正需要代理的用户，且无法重新启用。
- **带定期健康检查的自适应路由** — 已拒绝：对于本地中继来说过于复杂；用户需要的是最简单的仅故障切换机制，进程重启后重置。

后果：

- 默认安装走直连，因此 Clash 中断不再导致链路故障。
- 处于必需代理后面的用户必须显式配置 `--upstream-proxy` / `VISION_UPSTREAM_PROXY`。
- 粘性状态仅存在于内存中；重启代理后恢复默认顺序。
